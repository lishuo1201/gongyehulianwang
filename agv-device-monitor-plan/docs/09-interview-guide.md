## 4. 贯穿开发的场景训练

每轮选与当前任务相关的一个场景，按“业务场景 → 设计理由 → 项目证据 → 面试追问 → 未实现边界”练习。下列内容已提供分析方向，只作学习和复习；正式验收应换条件提问，每次一个问题，不提前给该题答案。

### 场景一：接入一台陌生设备（T01、T03～T05）

- **业务场景**：设备厂商只给出一个 IP，要求后端显示运行状态。先列出还缺少的信息，再决定接入方法。
- **设计理由**：确认协议/版本、端口、访问条件、Unit ID 或节点约定、点表、类型/单位/字节序、心跳、故障码、采集频率和联调环境；业务设备编码与协议寻址分别建模。具体概念见 [工业全景](02-architecture.md)。
- **项目证据**：使用 [固定寄存器样例](10-modbus-register-map.md)，后续对应 A03～A07 的解码及真实 TCP 记录；T01 初始化证据不能替代互通证明。
- **面试追问**：业务编号没变但 Unit ID 配错会怎样？报文长度正确、电量为 101 时，通信和业务质量分别如何判断？
- **未实现边界**：只实践项目自定义的 Modbus 模拟协议；OPC UA、MQTT、VDA 5050 是拓展理解，不宣称已经接过这些协议或真实 PLC。

### 场景二：显示在线，但数据一直不变（T06）

- **业务场景**：操作员认为设备停了，HTTP 和 Modbus 读取却都成功。
- **设计理由**：分别检查正常响应、业务心跳和运行状态；成功返回旧数据不能证明设备业务仍在刷新。
- **项目证据**：后续用 FROZEN 场景、lastResponseAt/lastFreshAt 及 A10/A11 验证，画出到达陈旧阈值前后的变化。
- **面试追问**：ONLINE + STALE 与 OFFLINE 的排错路径有什么不同？心跳从 65535 到 0 为什么需要单独覆盖？
- **未实现边界**：此心跳是模拟协议约定；实际设备可能没有相同机制，需向设备方核对，不能凭 Demo 保证现场数据新鲜度。

### 场景三：设备仍响应，数据库写入却失败（T07～T10）

- **业务场景**：采集日志有新数据，页面却没有更新；需要判断是通信、持久化还是推送出了问题。
- **设计理由**：按一次样本的时间与状态追踪采集、事务提交、已提交视图和 SSE；数据库失败不重置通信事实，页面也不能把未提交值显示为已保存。
- **项目证据**：P0 的 A14 验证事务回滚边界；readiness、DEGRADED 和恢复后缺口的完整数据库故障注入是 B03。分别引用实际执行结果，不能用回滚单测冒充停库验证。
- **面试追问**：如何区分采样时间、接收时间和 updatedAt？数据库恢复后是否补齐故障期间的历史？
- **未实现边界**：MVP 不保证故障期间零丢样本，不使用 MQ 补偿；没有实际运行的故障场景明确记为未验证。

### 场景四：下发搬运任务后响应超时（纯领域拓展）

- **业务场景**：Java 服务调用执行系统后超时，此时车辆可能已经开始动作。
- **设计理由**：区分请求成功、接收确认、动作完成与业务完成；先确认对端是否支持任务标识、幂等和状态查询，再制定有限重试、回执核对或人工处置方式。不能把只读采集的重试策略直接用于控制。
- **项目证据**：本项目没有任务下发或控制实现，无运行证据；使用 [架构中的控制边界](02-architecture.md)作概念讨论，回答后只记录领域理解。
- **面试追问**：厂商不支持幂等、结果又查不到时如何处理？重复或晚到回执应如何关联原任务？
- **未实现边界**：不新增控制 API、写寄存器或调度算法，不声称掌握 PLC 编程、运动控制或工业安全控制。

### 场景五：监控数据如何服务产线补料（贯穿各阶段）

- **业务场景**：生产侧提出物料需求，仓储侧安排出库，执行系统组织搬运，业务系统接收结果。使用 [产线补料案例](02-architecture.md)，说明这是示意分工。
- **设计理由**：设备台账、工单、库存和搬运任务是不同对象；通信地址不能代替业务关联。设备健康与历史可辅助异常定位，但车辆到站不天然代表装卸、库存过账或工序完成。
- **项目证据**：后续以真实监控页面、告警和历史记录说明“能够观察哪些设备事实”；不展示虚构的生产工单、物料或库存记录。
- **面试追问**：告警确认为什么不能解除实际故障？只靠本项目的数据，能否证明某一笔出库已完成，还缺什么证据？
- **未实现边界**：MES/WMS、WCS/RCS 属于职责与接口设计理解，不属于 Demo 的工程成果。

### 场景六：已有 Java 经验怎样迁移（T06～T13，T20 汇总）

- **业务场景**：面试官追问一个有 7 年经验的开发者在这个项目中作了哪些判断，而不只关心用了哪些框架。
- **设计理由**：用具体问题解释有界并发、超时预算、状态机、短事务、告警唯一约束和提交后推送；同时说明设备协议、数据质量及物理执行不确定性是需要补足的领域知识。
- **项目证据**：引用实际文件、运行命令和已完成用例；过去 Java 项目只引用自己确实承担的工作，不以本项目设计推定过去经历。
- **面试追问**：如果规模扩大或改成多实例，现有单设备 in-flight 与登记上限是否仍成立？先需要测什么、再决定改什么？
- **未实现边界**：扩展方案属于设计讨论；3 台模拟设备的结果不证明大规模、生产高可用或现场实施能力。

## 6. 主动纠正的几个概念

- PLC不是“某种通信协议”；Modbus TCP是通信方式之一，PLC/AGV是否支持取决于设备与供应商。
- OPC UA具有更丰富的信息模型能力，但不等于完全不需要配置、节点识别、类型映射或设备文档。
- `ONLINE`、`GOOD`、`RUNNING`属于不同维度；不能用一个status字段混在一起。
- 本项目unitId代表模拟器中的逻辑设备，不意味着所有真实AGV都以同样方式接入。
- “单实例正确”不等于“多实例正确”；多个后端可能重复采集、竞争更新，需要另外设计所有权。

领域概念用于学习，不作为该项目实际接入能力。协议事实以 [寄存器文档和官方来源](10-modbus-register-map.md) 为准。

4. **约60秒，事务与告警**：“网络读取在数据库事务外。收到合法样本后先生成候选，在一个事务中保存相关业务结果，成功后才替换内存基准。写库失败时保留旧业务值并显示降级。告警按设备和规则维护唯一活动槽，低于20触发、达到25恢复；确认只是知悉，恢复后再次异常会创建新记录。”
5. **约45秒，实时推送与验证**：“SSE发送已提交视图，采用有界待发队列，慢客户端不会直接占用采集线程或数据库事务。已有真实TCP、隔离MySQL、HTTP/SSE和浏览器测试，Compose报告记录三台模拟车30分钟观察及单车无响应、服务重启和数据库故障恢复。”
6. **约30秒，取舍与扩展**：“目前使用单实例和小规模全量视图，不引入消息队列或分布式采集。真实设备接入要重新核对厂商点表；多实例需要另行设计采集所有权。当前结果不能证明生产容量，缺失的历史也没有自动补偿。”

## 11. 八组面试追问与参考回答

这是用户要求的完整备稿，不属于正式考察。阅读答案后只算复习；独立验收仍换条件逐题进行，原答和学习状态保留在任务清单。

### 1. 只有设备IP，能否直接开始采集？Unit ID和设备编码是什么关系？

**参考回答**：还需要确认设备是否支持Modbus TCP、监听端口、Unit ID约定、功能码、寄存器地址与数量，以及字段类型、单位、字节序和更新规则。本项目按host、port和Unit ID定位读取对象，deviceCode仅用于平台管理，不进入读取报文。代码请求功能码03、起始地址0、数量8，再按固定点表解释16字节；同一监听地址可以区分三个模拟Unit。

**继续追问**：为什么不能把40001直接发出去？——本项目中40001是显示标签，对应PDU地址0。真实手册可能采用其他表示方法，不能把“减40001”写成通用规则。跨寄存器浮点数和字序也需要额外适配。

**定位与证据**：第10节协议接入行，以及[寄存器表](10-modbus-register-map.md)的固定字节样例。范围是自定义模拟协议；不能说已对接真实AGV、PLC或多个厂商。

### 2. 设备正常响应，为什么数据仍可能INVALID或STALE？

**参考回答**：连接状态回答是否收到正常响应，数据质量回答数值是否合法及是否足够新，运行状态表达设备业务含义。电量101超出协议范围，因此可以是ONLINE + INVALID；整组业务值不能被接受，但本轮正常响应仍更新通信时间。已接受心跳长期不变可以是ONLINE + STALE；RUNNING且速度0也可能表示任务中的等待，不能推断为空闲。

**继续追问**：心跳65535变成0是不是倒退？——本协议允许回绕，判断与上次已提交基准是否不同，不判断大小。首次基准为null，0是合法数值；新合法候选只有成功提交后才推进业务基准。两次采集之间恰好绕回同值时，当前协议无法还原中间过程。

**定位与证据**：DeviceState的response/watch、[DeviceSample](../backend/src/main/java/com/example/agv/protocol/DeviceSample.java)的hasNewHeartbeat、DeviceStateTest与验收B06。心跳是本项目约定，不能直接套用到没有心跳字段的设备。

### 3. 一台车读取超时，如何避免拖住其他车？

**参考回答**：调度器只提交任务，网络读取在有界工作线程池执行；每台设备的inFlight覆盖排队到持久化的完整周期，忙时跳过，不再叠加同车任务。每台车复用独立连接，关闭2号会话不会关闭1/3号。默认首次读取和至多一次重试共用1800ms预算，建连和请求等待各有阶段上限。健康扫描独立判断离线，不等待全部网络请求结束。

**继续追问**：停用又启用后，旧请求回来了怎么办？——任务保存开始时的配置版本，真正读取前和结果处理前都核对enabled及configRevision，旧结果不能覆盖新观察窗口。仅取消Future不能证明底层连接已关闭，需要实际释放连接资源。

**定位与证据**：MonitorService的scan/collect/current、ModbusTcpDeviceClient、MonitorConcurrencyIT与验收B01。线程池仍是共享的，多台同时卡住可能耗尽容量；已有证据只说明三台场景中的隔离行为，不是任意规模互不影响。

### 4. 原电量26，读到19却写库失败，页面应该显示多少？

**参考回答**：保持最后已提交的26，并显示采集降级，不能将未保存的19发布为可信业务结果。网络读取在事务外完成，正常响应事实独立记录；之后从旧业务基准复制候选，把快照、必要历史、状态事件和告警放入同一个事务。事务成功后才替换内存业务基准；失败丢弃候选，不能出现电量变成19但对应告警没有保存的结果。

**继续追问**：下一次收到与失败样本相同的心跳，能否再次保存？——可以与最后成功提交的心跳比较，因为失败样本没有推进基准。数据库恢复后可以接受新观测，但缺失区间没有可靠记录，不能自动补齐。内存保留了正常响应事实，也不意味着故障期间数据库的lastResponseAt已写入。

**定位与证据**：MonitorService的collect/persist/refreshView、MonitorRepository的persist/write、MonitoringPersistenceIT及验收B03。数据库恢复、视图恢复和设备通信是分别判断的状态；本项目没有持久化离线缓冲或零丢失保证。

### 5. 为什么要分别保存快照、历史采样和状态事件？

**参考回答**：快照用于回答当前最后可信值是什么；历史采样支持电量、速度等趋势查询；状态事件记录何时观察到连接、质量、运行状态或故障码变化。三者查询目的不同。项目首次新有效样本可记历史，后续距最后成功保存至少10秒且是新有效观测才再写；状态事件仅在相关字段变化时新增，避免每次心跳或电量变化都生成事件。

**继续追问**：两次轮询之间短暂停车，能从历史还原吗？——没有观察到就不能还原。事件时间是后端判定时间，不天然等于物理动作发生的精确时间。七天历史清理只处理采样表，按截止时间分批删除，每批最多1000行，不同步删除告警或状态事件。

**定位与证据**：DeviceState的historyDue、MonitorRepository的write/event、[HistoryRetention](../backend/src/main/java/com/example/agv/monitoring/HistoryRetention.java)、MonitoringPersistenceIT和P1MonitoringIT。有限轮询不能保证捕获所有物理事件，告警与事件也尚无同样的自动保留期限。

### 6. 告警如何去重？确认、恢复和停用有什么区别？

**参考回答**：数据库使用(device_id, rule_code, active_slot)唯一索引，ACTIVE的槽位为1，结束后为NULL，允许保存多次历史异常。持续异常更新同一记录的最后观测时间；确认只记录首次acknowledgedAt，不释放活动槽。低电量低于20触发、达到25恢复，20～24维持已有告警；有效观测19→25→19形成两次异常、两条记录。停用将活动告警抑制为SUPPRESSED，不表示设备物理异常消失。

**继续追问**：并发插入遇到唯一冲突怎么办？——先让整个外层事务回滚，再仅对识别出的uk_alarm_active冲突最多重试一次，重新读取数据库状态；不能捕获所有约束异常后都当作“告警已存在”。超时、非法或重复心跳也不能作为低电量恢复依据。

**定位与证据**：AlarmRules、MonitorRepository的transaction/alarm/ack、五表迁移、[BackendApplicationIT](../backend/src/test/java/com/example/agv/BackendApplicationIT.java)、MonitoringPersistenceIT。约束竞争和业务重试有各自用例，不宣称通过同一个端到端并发场景验证了所有交错；数据库约束也不等于已经解决多实例采集所有权。

### 7. 为什么选SSE？慢客户端和断线重连如何处理？

**参考回答**：页面需要服务端单向推送监控视图，登记、启停和确认仍走REST，因此采用SSE。监控服务在同一数据库读取事务中获取快照和活动告警，成功后整体替换不可变缓存；发送线程只读缓存，不持有采集锁或数据库事务。每连接最多保留两帧待发送全量视图，满时丢较旧待发帧，总连接数上限20，断开、超时或失败都做幂等清理。

**继续追问**：丢帧会丢掉告警吗？——数据库告警记录仍保留，丢的是页面中间视图；完整历史通过REST查询。重连获取当前全量，streamEpoch区分进程、sequence辅助拒绝旧帧，不承诺可靠事件回放。曾发现SseEmitter在MVC初始化前发送会进入框架早期缓冲，因此发送任务等待异步初始化完成后才开始写。

**定位与证据**：MonitorService的refreshView/view、StreamController、[页面脚本](../backend/src/main/resources/static/monitor.js)、MonitoringApiIT和StreamBackpressureIT。慢读用例采用加速推送制造背压，与默认1秒推送及30分钟观察是不同验收场景；全量视图方式只验证了当前小规模。

### 8. 接真实设备或扩成多实例，优先改变什么？

**参考回答**：真实接入先核对厂商协议和点表、设备网络条件、更新一致性与故障码规则，再为报文样例和异常场景补充适配测试。扩大设备量先测采集耗时、失败率、队列、连接、写库及推送负载，避免直接增加线程。多实例需要按设备划分采集所有权，并处理租约失效、旧实例结果隔离和幂等写入；当前进程内inFlight和配置版本检查不能直接解决跨实例竞争。

**继续追问**：是否应该立刻上MQ、Redis或微服务？——当前单实例三台模拟车没有这项需求。是否引入缓冲、消息系统或分片，应由容量、故障恢复目标和实测瓶颈决定。上线还需要认证授权、网络访问边界及运维方案，这些是后续设计事项。

**定位与证据**：[整体设计](12-code-design.md)、[架构与工业边界](02-architecture.md)、系统验收报告。此题中的真实硬件适配、多实例所有权与生产方案仅作扩展讨论，没有实现或运行证据；不写入简历的已完成事项。
