## 4. 贯穿开发的场景训练

每轮选与当前任务相关的一个场景，按“业务场景 → 设计理由 → 项目证据 → 面试追问 → 未实现边界”练习。下列内容已提供分析方向，只作学习和复习；正式验收应换条件提问，每次一个问题，不提前给该题答案。

### 场景一：接入一台陌生设备（T01、T03～T05）

- **业务场景**：设备厂商只给出一个 IP，要求后端显示运行状态。先列出还缺少的信息，再决定接入方法。
- **设计理由**：确认协议/版本、端口、访问条件、Unit ID 或节点约定、点表、类型/单位/字节序、心跳、故障码、采集频率和联调环境；业务设备编码与协议寻址分别建模。具体概念见 [工业全景](02-architecture.md)。
- **项目证据**：使用 [固定寄存器样例](10-modbus-register-map.md)，后续对应 A03～A07 的解码及真实 TCP 记录；T01 初始化证据不能替代互通证明。
- **面试追问**：业务编号没变但 Unit ID 配错会怎样？报文长度正确、电量为 101 时，通信和业务质量分别如何判断？
- **未实现边界**：只实践项目自定义的 Modbus 模拟协议；OPC UA、MQTT、VDA 5050 是拓展理解，不宣称已经接过这些协议或真实 PLC。

### 场景二：显示在线，但数据一直不变（T06）

- **业务场景**：操作员认为设备停了，HTTP 和 Modbus 读取却都成功。
- **设计理由**：分别检查正常响应、业务心跳和运行状态；成功返回旧数据不能证明设备业务仍在刷新。
- **项目证据**：后续用 FROZEN 场景、lastResponseAt/lastFreshAt 及 A10/A11 验证，画出到达陈旧阈值前后的变化。
- **面试追问**：ONLINE + STALE 与 OFFLINE 的排错路径有什么不同？心跳从 65535 到 0 为什么需要单独覆盖？
- **未实现边界**：此心跳是模拟协议约定；实际设备可能没有相同机制，需向设备方核对，不能凭 Demo 保证现场数据新鲜度。

### 场景三：设备仍响应，数据库写入却失败（T07～T10）

- **业务场景**：采集日志有新数据，页面却没有更新；需要判断是通信、持久化还是推送出了问题。
- **设计理由**：按一次样本的时间与状态追踪采集、事务提交、已提交视图和 SSE；数据库失败不重置通信事实，页面也不能把未提交值显示为已保存。
- **项目证据**：P0 的 A14 验证事务回滚边界；readiness、DEGRADED 和恢复后缺口的完整数据库故障注入是 B03。分别引用实际执行结果，不能用回滚单测冒充停库验证。
- **面试追问**：如何区分采样时间、接收时间和 updatedAt？数据库恢复后是否补齐故障期间的历史？
- **未实现边界**：MVP 不保证故障期间零丢样本，不使用 MQ 补偿；没有实际运行的故障场景明确记为未验证。

### 场景四：下发搬运任务后响应超时（纯领域拓展）

- **业务场景**：Java 服务调用执行系统后超时，此时车辆可能已经开始动作。
- **设计理由**：区分请求成功、接收确认、动作完成与业务完成；先确认对端是否支持任务标识、幂等和状态查询，再制定有限重试、回执核对或人工处置方式。不能把只读采集的重试策略直接用于控制。
- **项目证据**：本项目没有任务下发或控制实现，无运行证据；使用 [架构中的控制边界](02-architecture.md)作概念讨论，回答后只记录领域理解。
- **面试追问**：厂商不支持幂等、结果又查不到时如何处理？重复或晚到回执应如何关联原任务？
- **未实现边界**：不新增控制 API、写寄存器或调度算法，不声称掌握 PLC 编程、运动控制或工业安全控制。

### 场景五：监控数据如何服务产线补料（贯穿各阶段）

- **业务场景**：生产侧提出物料需求，仓储侧安排出库，执行系统组织搬运，业务系统接收结果。使用 [产线补料案例](02-architecture.md)，说明这是示意分工。
- **设计理由**：设备台账、工单、库存和搬运任务是不同对象；通信地址不能代替业务关联。设备健康与历史可辅助异常定位，但车辆到站不天然代表装卸、库存过账或工序完成。
- **项目证据**：后续以真实监控页面、告警和历史记录说明“能够观察哪些设备事实”；不展示虚构的生产工单、物料或库存记录。
- **面试追问**：告警确认为什么不能解除实际故障？只靠本项目的数据，能否证明某一笔出库已完成，还缺什么证据？
- **未实现边界**：MES/WMS、WCS/RCS 属于职责与接口设计理解，不属于 Demo 的工程成果。

### 场景六：已有 Java 经验怎样迁移（T06～T13，T20 汇总）

- **业务场景**：面试官追问一个有 7 年经验的开发者在这个项目中作了哪些判断，而不只关心用了哪些框架。
- **设计理由**：用具体问题解释有界并发、超时预算、状态机、短事务、告警唯一约束和提交后推送；同时说明设备协议、数据质量及物理执行不确定性是需要补足的领域知识。
- **项目证据**：引用实际文件、运行命令和已完成用例；过去 Java 项目只引用自己确实承担的工作，不以本项目设计推定过去经历。
- **面试追问**：如果规模扩大或改成多实例，现有单设备 in-flight 与登记上限是否仍成立？先需要测什么、再决定改什么？
- **未实现边界**：扩展方案属于设计讨论；3 台模拟设备的结果不证明大规模、生产高可用或现场实施能力。

## 6. 主动纠正的几个概念

- PLC不是“某种通信协议”；Modbus TCP是通信方式之一，PLC/AGV是否支持取决于设备与供应商。
- OPC UA具有更丰富的信息模型能力，但不等于完全不需要配置、节点识别、类型映射或设备文档。
- `ONLINE`、`GOOD`、`RUNNING`属于不同维度；不能用一个status字段混在一起。
- 本项目unitId代表模拟器中的逻辑设备，不意味着所有真实AGV都以同样方式接入。
- “单实例正确”不等于“多实例正确”；多个后端可能重复采集、竞争更新，需要另外设计所有权。

领域概念用于学习，不作为该项目实际接入能力。协议事实以 [寄存器文档和官方来源](10-modbus-register-map.md) 为准。

### 集中考察顺序

完成工程验收后再开始。每次只问一个变式，不先展示参考答案；原答、提示后的补正、独立变式结论分别记入 docs/06-tasks.md。

1. 接入与寻址：端点、Unit ID、业务别名、点表与字节缩放。
2. 数据判断：合法但重复、非法但有响应、心跳回绕及时间阈值。
3. 并发与取消：单车慢读、排队停用、旧revision结果、线程及连接回收。
4. 事务失败：通信事实与业务基准、整体回滚、下一次相同心跳。
5. 历史与事件：首次/间隔采样、状态转换、观测缺口和时间含义。
6. 告警生命周期：活动槽、19→24→25、确认、抑制、恢复后再触发。
7. REST/SSE：显式类型、已提交一致视图、降级、断线全量覆盖。
8. 工业与面试边界：监控如何辅助补料，为什么不能据此证明库存过账或安全控制。

可结合实际代码解释以下三项；测试通过只代表工程证据，不提前填写“本人独立掌握”。

- 数据质量：DATA_STALE表示在线但观察到心跳不推进，区别于通信离线和数据非法。只有新的有效提交才能恢复；数据库保存失败不能伪装成设备心跳冻结。
- 可靠性：连接池获取、驱动读和SQL超时解决不同等待环节；停库期间保留已提交视图并明确降级，恢复采集不等于补齐丢失历史。长时观察的实际环境、范围与结果以验收报告为准，不将半小时当生产SLA。
- 资源与保留：SSE发送等待HTTP初始化、每连接最多两帧、慢读合并旧帧；7天采样历史按日分批清理，单批1000行，告警与事件另行保留。默认3台模拟车，不能将有界队列描述为已通过大规模压测。

若需补充演示数据陈旧：`scripts/scenario.sh 1 FROZEN`后等待超过10秒，观察ONLINE + STALE与DATA_STALE；切INVALID不能恢复，再切NORMAL观察恢复。此流程延长原3～5分钟操作单，不挤压为未等阈值就宣布成功。
