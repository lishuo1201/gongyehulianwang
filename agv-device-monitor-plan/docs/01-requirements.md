# 01 需求与验收边界

状态：P0/P1代码及工程验收已完成；准确证据和学习进度见[任务交接](06-tasks.md)。所有阈值都是本地 Demo 的约定，不是行业标准。

## 1. 项目目标

面向已有 7 年 Java 互联网开发经验、工业领域基础不足的开发者，目标岗位为工业软件 Java 后端。通过项目掌握“设备协议 → 后端采集 → 状态管理 → 数据保存 → 异常告警 → 页面展示”，能解释数据从哪里来、失败如何处理，以及这些设备事实怎样服务工业业务。

开发预算约 5～10 个开发日、每天 2～4 小时。先保证数据链路真实、行为可验证，再做展示美化。

学习目标分三层，不能把认识范围写成工程完成范围：

- **已有经验按需复习**：复用 Java 接口、并发、事务和数据建模经验；Maven/Spring/CRUD 不默认设入门考试，必要的工程验证照常执行。
- **项目必须实践**：按下方 P0 实现只读采集监控，用真实协议、数据库和运行证据解释数据质量、告警、事务及展示行为。
- **工业拓展理解**：能画出设备/PLC、协议接入、Java 业务服务、MES/WMS/调度及 Web 的职责图，解释数据上报、任务下发、执行反馈；理解控制与采集的区别，以及 OPC UA/MQTT/VDA 5050 的用途和边界。此层不新增工程功能。

全景与产线补料案例见 [架构](02-architecture.md)，分阶段教学见 [学习计划](05-development-plan.md)，场景追问见 [面试训练](09-interview-guide.md)。你负责设计、预测及解释，Codex 编码和运行验证；学习通过不要求亲手编码，也不由工作年限自动认定。

## 2. P0：MVP 必须完成

| 编号 | 需求 | 可观察的完成标准 |
| --- | --- | --- |
| R01 | 设备登记 | 可查询、新增、修改名称、启停采集；设备编码唯一 |

| R07 | 实时页面 | 设备列表、详情、告警表、最近历史；SSE 实时刷新 |
| R08 | 可复现部署 | 本地 Compose 启动 3 个服务，有健康检查和数据卷 |

## 5. 默认参数：唯一事实来源

| 配置键 | 默认值 | 含义 |
| --- | --- | --- |
| `poll.interval-ms` | 1000 | 调度扫描周期；繁忙设备跳过本轮 |
| `poll.connect-timeout-ms` | 800 | 建连等待上限 |
| `poll.request-timeout-ms` | 800 | 单次读取响应等待上限 |
| `poll.cycle-budget-ms` | 1800 | 含建连、一次重试的整轮总预算 |
| `poll.max-attempts` | 2 | 首次尝试 + 最多一次重试，不是重试两次 |
| `poll.retry-delay-ms` | 100 | 同轮重试间隔，受整轮预算约束 |
| `poll.workers` | 4 | 采集工作线程数 |
| `poll.queue-capacity` | 16 | 有界等待队列容量；满时跳过并计数 |
| `device.offline-ms` | 10000 | 未收到有效协议响应的离线阈值 |
| `device.stale-ms` | 10000 | 心跳无推进的数据陈旧阈值 |
| `device.watchdog-ms` | 1000 | 独立健康扫描周期 |
| `history.interval-ms` | 10000 | 正常历史采样最小间隔 |
| `history.retention-days` | 7 | 每日清理早于保留截止时间的采样；每批最多1000行 |
| `alarm.battery-trigger-below` | 20 | 电量严格小于 20% 触发 |
| `alarm.battery-recover-at-least` | 25 | 电量大于等于 25% 恢复，避免抖动 |
| `sse.heartbeat-ms` | 15000 | 浏览器 SSE 保活，与设备心跳不同 |
| `sse.snapshot-ms` | 1000 | SSE 全量视图推送周期 |
| `demo.max-devices` | 10 | 第一版登记上限；默认 3 台 |

参数启动时校验：均为正数、恢复阈值大于触发阈值、单轮预算小于离线阈值。T01/T05 必须验证库实际超时语义；总预算不能靠累加配置值推算后直接声称满足。

## 6. 三类状态

| 维度 | 枚举 | 含义 |
| --- | --- | --- |
| `connectionStatus` | UNKNOWN / ONLINE / OFFLINE / DISABLED | 通信及采集启用情况 |
| `dataQuality` | UNKNOWN / GOOD / STALE / INVALID | 数据是否可信、是否持续更新 |
| `runState` | UNKNOWN / IDLE / RUNNING / CHARGING / FAULT | 设备最近一次可信的运行状态 |

- `ONLINE` 不保证 `GOOD`：能读到寄存器也可能一直是旧数据。
- `OFFLINE` 不等于 `FAULT`：前者是通信问题，后者是设备故障。
- 无数据用 `null` / UNKNOWN，不使用电量 0、速度 0 冒充实测值。
- 离线后保留旧值，但显式显示数据陈旧、最后更新时间。
- 后端重启先重新验证通信，不能仅从数据库读出旧 ONLINE 就显示设备在线。

详细状态转换以 [架构](02-architecture.md) 为准。

## 7. 告警规则

| 规则 | 触发 | 恢复 |
| --- | --- | --- |
| LOW_BATTERY | 新的 GOOD 样本电量 < 20 | 新的 GOOD 样本电量 >= 25 |
| DEVICE_FAULT | 新的 GOOD 样本故障码 != 0 | 新的 GOOD 样本故障码 = 0 |
| DEVICE_OFFLINE | 通信健康扫描判断 OFFLINE | 收到有效 Modbus 正常响应 |
| DATA_STALE（P1） | ONLINE、STALE，且最近合法响应重复已提交的心跳，距最后有效样本至少10秒 | 新的GOOD样本成功提交；重启后首次有效样本也重新建立基准 |

GOOD 样本的故障码与运行状态须一致，详见寄存器表。无可信新样本时不自动恢复低电量和故障告警。

DATA_STALE为WARNING；INVALID、OFFLINE和加载重启旧值均不单独触发或恢复该告警。数据库保存失败时的新心跳也不算设备心跳冻结；保持已有告警，等待新的有效提交。确认只记录知悉，停用仍按统一规则抑制。

同一设备同一规则只存在一个未恢复事件；持续异常更新最近观测时间，不持续插新记录。用户确认只记录知悉，不把故障改成正常。停用设备将未恢复告警标记为 SUPPRESSED，而非正常 RECOVERED。

## 8. MVP 的停止条件

以下全部满足才可称“完成 MVP”：

- 真实 TCP 读取 3 台模拟设备，不使用随机 REST 数据替代采集。
- 低电量、故障、掉线及恢复按规则可复现，持续异常不会刷屏。
- 页面能分辨旧数据与新数据；历史查询带分页和时间范围。
- 在本机完成干净数据库启动、正常重启及 P0 自动测试。
- README 有实际可执行的启动方式和已知限制。
- 所有证据能追溯到命令、测试报告或实际截图；未执行项明示。
